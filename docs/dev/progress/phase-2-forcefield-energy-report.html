Model Asset Normalization

The packaged model is now a single H5 asset. This removes the old runtime split between 6spn.h5, cranberry0.2.19.h5, --nonbonded-para, and --base-para. The old --angle-scaling 0.1 default is baked into the angle spring constants.

Public System Builder

CranberryForceField follows the OpenMM shape: construct the force field object, then call createSystem() with an OpenMM topology. Temperature and salt enter here because Debye-Huckel electrostatics are temperature/salt dependent.

    def __init__(self, model: str = "default"):
        self.spec = get_model_spec(model)
        self._xml = app.ForceField(str(self.spec.xml_path))

    def createSystem(

Spline Port

The spline implementation is a direct port of the legacy 6spn + high spline + base-form aniso behavior. It uses the 12-type high-resolution mapping and base_idx_lim=3, so spline handles P/S interactions while base-base interactions are handled by stacking/pairing.

def _add_spline(self, system: mm.System, data: _TopologyData, base_idx_lim: int) -> None:
    y_nodes = self._params["spline_y_nodes"]
    x_lim = self._params["spline_x_lim"]
    n_types = y_nodes.shape[0]
    expr = "0"
    active_pairs: list[tuple[int, int]] = []
    for i, j in product(range(n_types), range(n_types)):
        if i < base_idx_lim or j < base_idx_lim:
            expr += f"+delta(type1-{i})*delta(type2-{j})*U{i}{j}(r)"
            active_pairs.append((i, j))

The OpenMM tabulated functions come directly from the H5 nodes. Virtual sites are excluded by applying the interaction group only to real sites.

for i, j in active_pairs:
    force.addTabulatedFunction(
        f"U{i}{j}",
        mm.Continuous1DFunction(y_nodes[i, j], float(x_lim[i, j, 0]), float(x_lim[i, j, 1])),
    )
force.addPerParticleParameter("type")
for name in data.atom_names:
    force.addParticle([HIGH_RES_SPLINE_TYPES[name]])
force.addInteractionGroup(data.real_site_ids, data.real_site_ids)
force.createExclusionsFromBonds(data.bonds, 3)

Sugar Pucker Port

The sugar-pucker path uses the simpler single-force mode instead of the legacy all-log reporter-oriented path. This keeps Phase 2 focused on correct system energy construction; detailed sugar logging can return with MD/reporters.

def _add_sugar_pucker(self, system: mm.System, topology: app.Topology) -> None:
    descriptors = [name for name in self._params["sugar_sigmoid"] if name != "intercept"]
    expression = self._sugar_pucker_expression(descriptors)
    force = mm.CustomCompoundBondForce(6, expression)
    force.addGlobalParameter("a0", 2 * np.log(99) / 108)
    force.addGlobalParameter("P0", 90)
    force.addGlobalParameter("kg", float(np.ravel(self._params["sugar_gaussian"]["k"])[0]))
    force.addGlobalParameter("dU_C2endo", float(np.ravel(self._params["sugar_dU"])[0]))

The expression keeps the legacy sigmoid/gaussian interpolation between C3'-endo and C2'-endo terms.

expression = "((1-sigmoid)*U3+sigmoid*(U2+dU_C2endo))*(1-gaussian); "
expression += "sigmoid=1/(1+exp(-a0*(P-P0))); "
expression += "gaussian=kg*exp(-a1*(P-P1)^2); "
expression += "P=" + self._phase_angle_expression(descriptors)
expression += "U3=" + self._sugar_u_expression(descriptors, state="3")
expression += "U2=" + self._sugar_u_expression(descriptors, state="2")

Energy API And CLI

The Python energy API validates input, builds the system, uses the PDB-provided virtual-site coordinates, and reports total plus force-group energies. It intentionally does not call Context.computeVirtualSites() in the regression path, matching the legacy workshop posthoc_energy.csv evaluator.

def compute_energy(...):
    validation = validate_canonical_pdb(pdb_path)
    validation.raise_for_errors()

    pdb = app.PDBFile(str(pdb_path))
    forcefield = CranberryForceField(model)
    system = forcefield.createSystem(
        pdb.topology,
        positions=pdb.positions,
        temperature=temperature,
        salt_concentration=salt_concentration,
    )
    ...
    simulation.context.setPositions(pdb.positions)
    simulation.context.computeVirtualSites()

The CLI remains thin and converts shell strings/numbers into API arguments.

energy_parser = subparsers.add_parser("energy", help="compute total and decomposed CRANBERRY energies")

Regression Tests

The new tests assert both construction shape and numeric energy behavior. These are not final workshop parity proofs; they are fast CPU regression guards for the packaged implementation.

def test_create_system_adds_named_forces():
    pdb = app.PDBFile(str(data_path("examples/2ntCG_cg_vs_conect.pdb")))
    system = CranberryForceField().createSystem(pdb.topology, positions=pdb.positions)
    names = {system.getForce(index).getName() for index in range(system.getNumForces())}
    assert {"bond", "angle", "dihedral", "pucker", "stacking35", "stacking55", "stacking33", "pairing", "wca", "spline", "electrostatic"} <= names
@pytest.mark.parametrize("filename,expected", EXPECTED_ENERGIES.items())
def test_energy_regression_cpu(filename, expected):
    report = compute_energy(data_path(f"examples/{filename}"), platform="CPU")
    values = report.as_kj_per_mol()
    for name, value in expected.items():
        assert values[name] == pytest.approx(value, abs=1e-6)

Risk Review

  • Scientific parity: the code follows the legacy formulas, but exact parity against workshop logs has not yet been independently audited.
  • Code size: forcefield.py is larger now because it directly encodes the canonical force construction. It avoids extra framework layers, but may deserve careful module splitting after MD/reporters arrive.
  • Dependency: base runtime now depends on h5py because the canonical model asset is HDF5.
  • No PBC path yet: Phase 2 energy construction is non-periodic, matching the immediate CPU regression use case. PBC/box handling belongs with MD.
  • Pre-v1 documentation: before release, add force-construction comments/docs for bonds, angles, dihedrals, sugar pucker, stacking, pairing, WCA, spline, and electrostatics so the OpenMM-CGRNA mapping is easy to audit.

Recommended Next Step

Before Phase 3 MD/reporters, run a focused workshop parity audit: generate energies from the workshop implementation for the same four fixtures, compare component-by-component, and document any intentional differences.

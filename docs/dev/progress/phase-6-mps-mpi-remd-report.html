CRANBERRY Phase 6 MPS/MPI REMD Report

This report covers the MPS/MPI adaptation slice requested after comparing the cleaned Cranberry package with the legacy 04-cranberry/melting_v2_cedric launch behavior. It also records the follow-up REMD restart work tracked in GitHub issue #9.

Implemented

  • Added repeatable --platform-property KEY=VALUE support to cranberry md and cranberry remd.
  • Threaded OpenMM platform properties through create_simulation, run_md, and the OpenMMTools REMD context cache.
  • Added runtime provenance for platform properties, CUDA_VISIBLE_DEVICES, CUDA MPS pipe/log directories, and parent GPU visibility.
  • Made Cranberry-owned REMD side effects rank-0-only when mpiplus detects MPI: output directory creation, output existence checks, args.json writes, DCD extraction, and CLI summaries.
  • Added serial/MPI metadata to REMD args.json, including detected rank/size and common OpenMPI, PMIx, Slurm, and launcher environment values.
  • Added optional JAX metadata capture when online analysis is enabled: JAX/JAXLIB versions, default backend, and device strings. JAX remains optional and is not imported when --n-analysis 0; detailed backend/device discovery is deferred until after the sampler run so it does not initialize JAX GPU memory before OpenMM starts.
  • Added cluster launch helpers under scripts/hpc/ for REMD MPI+MPS and independent MD MPS packing.
  • Hardened mpi_runtime_env.sh for interactive Slurm shells by clearing stale PMI/PMIx/OMPI rank bootstrap variables before launching Cranberry's own mpirun.
  • Aligned the REMD MPI+MPS wrapper with legacy benchmark logging: N_RECORD=10000 by default, worker output captured to stdout.log/stderr.log, and live tee streaming available only with STREAM_LOG=1.
  • Added wrapper diagnostics for CPU allocation and JAX backend: launcher_env.txt now records Slurm CPU fields and processor affinity, while preflight.log records OpenMMTools/mpi4py import status and the JAX backend/device list.
  • Added a wrapper warning when the detected CPU allocation is smaller than N_MPI_RANKS, because oversubscribing CPU cores can strongly affect MPS throughput.
  • Added scripts/hpc/submit_cacag_5us_pbc_l40s.sh, a self-submitting 5 us CACAG PBC production sbatch helper for the Torch L40S allocation. It uses a 47 h internal timeout inside a 48 h Slurm allocation and resubmits itself after timeout/kill exits until the NetCDF stored iteration reaches the 5 us target.
  • Made the production submitter resolve CONDA_ENV=cranberry-dev to $HOME/.conda/envs/cranberry-dev by default, prepend that environment's bin directory inside the batch job, pass the resolved Python through PYTHON_BIN, and run a submit-side preflight for openmmtools, mpi4py, and netCDF4.
  • Added optional MAX_RESUBMITS / RESUBMIT_COUNT controls so timeout/restart behavior can be tested with a short run without creating an unbounded resubmission loop.
  • Made the production helper log current and target progress in iterations, steps, ns, and us, plus the derived per-attempt checkpoint and analysis intervals. The restart branch now explicitly refuses to resubmit when the stored NetCDF iteration is at or above the target.
  • Changed the production submitter's default online-analysis cadence to mirror the old melting v2 pt_online_analysis_interval=null formula when N_ANALYSIS is unset. For the default 5 us production target this gives target_analysis_interval=200 REMD iterations and full_run_n_analysis=1000, rather than only 10 analyses across the full run.
  • Added scripts/hpc/submit_ggcGCAAgcc_5us_nopbc_l40s.sh, a small no-PBC production wrapper that reuses the restart-tested L40S submitter while setting the ggcGCAAgcc canonical/extended seed PDBs, no-PBC mode, the melting v2 310-410 K temperature range, a distinct job name, and a distinct output directory.
  • Hardened REMD restart storage handling for cranberry remd --restart-from. The restart path now closes Cranberry's read-only validation reporter before sampler restoration, and MPI restarts use a Cranberry _sampler_from_storage helper that mirrors OpenMMTools restoration while inserting an MPI barrier before rank 0 opens the NetCDF reporter in append mode.
  • Removed the production submitter's special NetCDF-HDF exit-code-1 retry loop. Only timeout/kill exits 124 and 137 now trigger automatic resubmission; restart failures with exit code 1 fail visibly instead of waiting five minutes and retrying.
  • Updated REMD docs to distinguish the low-risk --n-analysis 0 mode from the old melting-style JAX GPU online-analysis path.

REMD Restart Finding

The production CACAG restart failed at ParallelTemperingSampler.from_storage(...) with NetCDF: HDF error while reopening runs/cacag_pbc_5us_l40s_prod_analysis200/output.nc. The same NetCDF opened successfully read-only with netCDF4.Dataset, and a disposable copy opened successfully through single-process OpenMMTools from_storage. This points away from simple file corruption and toward MPI restart-open ordering.

OpenMMTools from_storage opens the storage in read mode on all ranks, restores sampler state, closes the reporter, and then opens append mode on rank 0 with sync_nodes=False. On larger production files, rank 0 can reach append-open while another MPI rank is still reading or closing. The branch mitigation keeps non-MPI behavior delegated to OpenMMTools but uses a synchronized restore path under MPI: read/restore/close on all ranks, MPI barrier, then rank-0 append-open with sync_nodes=True.

The tiny 10-minute restart smoke and the later ggcGCAAgcc continuation do not disprove the race. The small smoke file likely restored fast enough on all ranks, and ggcGCAAgcc had earlier HDF restart failures before a later attempt progressed beyond iteration 39180. Both behaviors are consistent with nondeterministic timing.

Legacy Match Notes

The old melting worker set OPENMMTOOLS_ENABLE_MPI=1, launched the same OpenMMTools parallel tempering code under MPI, started CUDA MPS, and mapped multiple local MPI ranks onto one or more GPUs. Cranberry now preserves that architecture through the standard cranberry remd command instead of adding a separate experimental REMD command.

The helper scripts/hpc/run_cranberry_remd_mpi_mps.sh defaults to N_ANALYSIS=10. For a 500000-step run with SWAP_STEPS=5000, this produces an online-analysis interval of 10, matching the legacy OpenMMTools automatic interval seen in the old melting runs. It does not force JAX_PLATFORM_NAME=cpu, so JAX can use its default backend when the GPU JAX build is loaded.

The legacy melting_v2_cedric 500000-step CACAG benchmark used N_RECORD=10000 and printed checkpoint interval is 1, online analysis interval is: 10. A current 50000-step smoke run with N_RECORD=10 produced checkpoint_interval=5 and N_ANALYSIS=0, so it wrote less often than the legacy run. Logging/checkpoint volume is therefore unlikely to explain the observed throughput gap by itself, but the wrapper now defaults to the legacy logging shape for cleaner A/B timing.

The same legacy benchmark used salt=1000, t_min=280, t_max=380, padding=2.0, and an alternate extended starting PDB. The observed slow 50000-step Cranberry smoke run used salt=150, t_min=298, t_max=600, padding=2.25, and no alternate starting PDB. These physical/run-setup differences, especially the lower salt and larger validated electrostatic cutoff, are stronger throughput suspects than log volume.

The saved legacy GPU snapshot for cacag_1gpu shows an NVIDIA L40S. A later matched Cranberry run was started on an NVIDIA H200 with MIG disabled and reported about 1.25-1.40 aggregate microseconds/day in output_real_time_analysis.yaml through iteration 40. Because online MBAR/JAX analysis was active, the next A/B should compare the same H200 allocation with N_ANALYSIS=0 before attributing the difference solely to H200 versus L40S or CPU allocation.

A follow-up L40S run on l40s_courant reported GPU JAX in preflight.log and improved to about 1.75 aggregate microseconds/day through iteration 20, but the allocation exposed only SLURM_CPUS_PER_TASK=4 with CPU affinity to four cores for N_MPI_RANKS=8. The legacy benchmark submitter used CPUS_PER_TASK=32. This CPU allocation difference is now the most concrete remaining explanation for the gap to the old 3.33 aggregate microseconds/day result.

The 5 us production helper treats TARGET_STEPS=1000000000 and SWAP_STEPS=5000 as 200000 target REMD iterations. Because Cranberry's current restart path calls OpenMMTools extend(n_iterations), the helper reads output.nc before each attempt and launches only the remaining iterations. It preserves the full-run logging cadence by deriving per-attempt N_RECORD and N_ANALYSIS from the target checkpoint and online-analysis intervals.

For production runs with N_ANALYSIS unset, the target online-analysis interval follows the old OpenMM-CGRNA melting v2 default: max(min(target_iterations / 10, 10 * target_checkpoint_interval), 1). With the default 5 us setup this evaluates to analysis every 200 REMD iterations, about 5 ns per replica, while N_ANALYSIS=0 still disables online analysis explicitly.

The production helper now exports CRANBERRY_REPO_ROOT, CRANBERRY_SUBMIT_SCRIPT, and CRANBERRY_REMD_HELPER into each Slurm submission. This avoids resolving paths relative to Slurm's spooled script copy, which can live under scheduler-owned directories such as /opt/slurm/data.

The production helper prepares the Python environment inside each Slurm job instead of relying on the user's interactive shell activation state. By default it uses $HOME/.conda/envs/cranberry-dev/bin/python; CONDA_ENV, CONDA_ENV_PATH, and PYTHON_BIN remain overrideable for alternate environments.

The ggcGCAAgcc no-PBC production wrapper intentionally delegates to the same submitter rather than duplicating restart logic. It overrides USE_PBC=0, T_MIN=310, T_MAX=410, JOB_NAME=ggcGCAAgcc_5us_nopbc, OUTPUT_DIR=runs/ggcGCAAgcc_nopbc_5us_l40s, and the corresponding canonical/extended seed PDB paths.

Risks And Follow-Up

  • The copied-production CACAG restart smoke is still pending. The prepared directory runs/cacag_restart_barrier_test_from_prod_copy contains copied production restart artifacts and should be tested with a short Slurm run before retrying the real CACAG production directory.
  • CUDA/MPI/MPS throughput has not been fully validated in this report. Some cluster smoke/prod runs were started during debugging, but a clean post-fix benchmark comparison is still needed.
  • The MPI behavior relies on OpenMMTools/mpiplus for sampler distribution. Cranberry now avoids duplicate Cranberry-owned writes, but true MPI correctness still depends on running under mpirun or srun with working mpi4py.
  • --n-analysis 0 remains the simplest way to avoid JAX overhead or JAX CUDA memory pressure. Matching the old melting performance path should use a GPU JAX build with nonzero N_ANALYSIS.

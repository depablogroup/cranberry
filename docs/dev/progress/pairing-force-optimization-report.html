Pairing Force Optimization Report

Date: 2026-08-09

Branch: optimize-bp

Summary

The base-pairing force was the dominant CUDA bottleneck in the local 1l2x ablation benchmark. The original implementation used one large CustomHbondForce containing all 25 geometric pairing terms gated by donor and acceptor base-type delta(...) factors. This means every candidate donor/acceptor pair carried the full expression even when most terms were inactive for that base-type pair.

The first optimization grouped the 25 geometry rows into 9 donor/acceptor base-type forces. The third pass packed those rows into 4 donor-specialized forces. A fourth pass moved the already selected parameter slots directly onto each acceptor, removing the Discrete1DFunction lookups while keeping the same four kernels and no runtime type branches. The latest pass uses one explicit pair-parallel compound force for nontrivial systems with at most 8192 valid directed residue pairs and retains the donor-specialized neighbor-list implementation as the scalable fallback. All forces retain name pairing and force group 14. Same-chain near-residue pairs are omitted from the compound bond list and remain explicit CustomHbondForce.addExclusion() entries in the fallback. The guarded dihedral construction is unchanged.

The retained stacking pass fuses stacking35, stacking55, and stacking33 into one CustomHbondForce. It traverses candidate base pairs and computes distance, angles, dihedral, and normal geometry once. Global scale parameters preserve exact component reporting without adding extra forces to normal MD.

Each donor type gets one specialized force. Only compatible acceptor residues are registered, so no acceptor-validity branch is needed. Parameter slots are stored directly on each acceptor, and zero-amplitude slots pad type pairs with fewer rows. The public energy decomposition remains unchanged.

Second Optimization Pass

A direct-dihedral shortcut was tested as a possible optimization, but it was rejected: idealized collinear configurations produced NaN energies on CUDA. The original guarded construction is retained. An earlier four-force donor-type regrouping was discarded because its explicit acceptor-type dispatch outweighed the reduction in force kernels.

Third Optimization Pass

Nsight Compute showed that the 9 typed forces launched 9 one-block computeHbondForces kernels per step. The retained branch-free donor packing reduces this to 4 launches. The earlier 370 us nine-kernel figure was not an isolated like-for-like capture and is not used to quantify the gain. The clean evidence is the repeated end-to-end benchmark below. A guarded trigonometric common-subexpression rewrite was energy-exact but unchanged in wall time, showing that OpenMM already optimized those expressions. A transformed-parameter packed variant was also exact but slightly slower than retaining the original 13 parameters.

Fourth Optimization Pass

The four donor-specialized forces originally fetched each slot parameter from a four-entry table indexed by acceptor type. Since an acceptor's type is fixed when the OpenMM System is created, the final implementation resolves those values in Python and stores them as per-acceptor parameters. Eight interleaved full-model repeats measured 1.236 +/- 0.037 s for the table-backed form and 1.189 +/- 0.010 s for direct acceptor parameters, a 3.9% end-to-end gain. A focused Nsight Compute capture kept the same four one-block launches and reduced their instrumented total from about 147 us to 136 us.

Fifth Optimization Pass

CustomHbondForce assigned the 1l2x workload to one 128-thread block per donor channel. Each donor thread then traversed its compatible acceptors. Partial channel fusion reduced four launches to two but improved the whole model by only about 3%, because table dispatch, padded slots, and register growth consumed most of the launch saving.

The retained small-system path instead creates one six-particle CustomCompoundBondForce bond per valid directed residue pair. The immutable bond stores the donor and acceptor COG, normal, and B1 particle indices plus its preselected base-type parameters. Coordinates, distance, angles, and guarded dihedrals remain dynamic. A step(0.8-r) factor preserves the original runtime cutoff, and periodic compound geometry uses OpenMM minimum-image displacements. Same-chain sequence-neighbor pairs are omitted when the bond list is built.

1l2x contains 336 valid pairing bonds. Ten interleaved full-model CUDA repeats measured 0.9098 +/- 0.0164 s per 5000 steps for the retained four-channel fallback and 0.5748 +/- 0.0121 s for the pair-parallel path. This is a 36.8% wall-time reduction and a 1.58x throughput increase. Nsight Compute measured the old four pairing kernels at about 137 us total. The new computeBondedForces kernel takes 18.9 us, using six 64-thread blocks and 255 registers per thread.

All four canonical CPU pairing energies remain within 1e-6 kJ/mol. On a deterministically perturbed 1l2x configuration, compound and fallback energies differ by 5.68e-14 kJ/mol and the largest force-component difference is 2.84e-14 kJ/mol/nm, identically for periodic and nonperiodic systems. Exact collinear donor stress tests retain finite CUDA energies and forces. Systems above 8192 valid pairs continue to use the neighbor-list implementation to avoid quadratic storage and work. One-channel, one-slot systems such as rU40 also retain that path because explicit pairs provide no repeatable benefit there.

Direct CPU comparisons on the same seven initial configurations found zero pairing-energy difference for six systems and 5.68e-14 kJ/mol for 1l2x. The largest absolute force-component difference was 9.1e-13 kJ/mol/nm for 2MI0; 5ml7 was 6.8e-13 kJ/mol/nm. These are floating-point accumulation differences.

The benefit therefore persists through the largest packaged benchmark, but this does not establish that explicit pairs win at arbitrary size. Systems exceeding 8192 valid pairs use the neighbor-list fallback by design, so they receive neither a compound-path speedup nor its quadratic runtime and storage cost.

A synthetic crossover check replicated 2MI0 into separate chains translated 10 nm apart. Cross-copy pairs were therefore outside the cutoff, deliberately favoring the H-bond neighbor list and penalizing explicit compound traversal. Compound wall-time reductions were 38.5% at 8805 pairs, 32.3% at 15,752 pairs, 26.9% at 24,705 pairs, and 16.8% at 35,664 pairs. The paths were effectively tied at 63,600 pairs (1.1% compound advantage), and compound was 23.6% slower at 99,560 pairs. The observed RTX 2060 crossover is consequently near 60,000 pairs for this sequence composition. The production 8192-pair bound remains intentionally conservative because OpenMM selects the force representation before the eventual CPU or GPU platform is known, and crossover behavior depends on platform and slot composition.

Spline And Stacking Experiments

Precomputing the two constant stacking cosines was energy-exact but 0.7% slower in an unfused interleaved benchmark; that isolated rewrite was rejected. The retained fused implementation instead shares all geometric work and evaluates the three parameterized energies in one expression. Scale parameters are set to one during dynamics. Energy and MD reporting temporarily isolate each scale, evaluate the single stacking group, and restore the previous context values.

Nsight Compute measured three unfused one-block kernels at approximately 41 us each, or 124 us total. The fused kernel takes 46 us. Register use rises from 80 to 113 per thread, but eliminating two launches and duplicate geometry reduces instrumented stacking kernel time by about 63%.

Eight interleaved repeats measured 1.154 +/- 0.022 s before fusion and 0.913 +/- 0.015 s after fusion, a 26.4% whole-model speedup. The independent five-repeat production timing is 0.901 +/- 0.018 s, or 2398 ns/day, compared with 1.159 +/- 0.023 s before fusion. This is a 22.3% reduction in wall time.

Spline interaction pruning was also investigated. Explicitly enumerating active pairs was exact and appeared 8.2% faster on 1l2x, but required quadratic pair-list storage. A scalable single-group version preserved the asymmetric legacy table orientation and all regression energies, but improved wall time by only 0.45%, within noise. Neither spline variant was retained.

Risks And Follow-Up

  • Small systems contain one compound force named pairing. Systems above the explicit-pair threshold contain multiple H-bond forces with that name; all intentionally share force group 14.
  • Nsight Compute 2022.4 was extracted under /tmp/nsight-local and used for kernel-level profiling; it is not a project dependency.
  • A one-force-per-geometry experiment passed energy regression but was slower on CUDA: about 2.805 s per 5k all-force steps, so it was discarded.
  • The CUDA benchmark is short and intended for local directionality, not a publication snapshot.
  • The fused stacking force occupies the force group of its first enabled stacking component. Separate component values remain available through Cranberry's energy-reporting APIs, but direct external OpenMM force-group queries no longer map groups 11, 12, and 13 to three runtime forces.
  • The 8192-pair threshold bounds explicit parameter storage but is a conservative engineering cutoff, not a measured crossover for every GPU architecture and sequence composition.

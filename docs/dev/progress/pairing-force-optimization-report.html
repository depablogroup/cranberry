Pairing Force Optimization Report

Date: 2026-08-06

Branch: optimize-bp

Summary

The base-pairing force was the dominant CUDA bottleneck in the local 1l2x ablation benchmark. The original implementation used one large CustomHbondForce containing all 25 geometric pairing terms gated by donor and acceptor base-type delta(...) factors. This means every candidate donor/acceptor pair carried the full expression even when most terms were inactive for that base-type pair.

The optimized construction groups the 25 geometry rows into 9 donor/acceptor base-type forces. Each force includes only compatible residues and only the geometry rows for that type pair. All split forces retain name pairing and force group 14, so energy decomposition and detailed reporting still see one public pairing component. A second pass moved same-chain near-residue pairing exclusions from the CUDA expression into explicit CustomHbondForce.addExclusion() entries, removing runtime step, abs, and chain-id delta gates from every candidate interaction.

The helper namespaces global parameters per split force because OpenMM requires same-named global parameters across forces to have identical default values. Donor/acceptor metadata is used at construction time only to add same-chain exclusions; the force expression no longer carries residue-id or chain-id per-particle parameters.

Risks And Follow-Up

  • The system now contains multiple OpenMM forces named pairing; they intentionally share force group 14.
  • A one-force-per-geometry experiment passed energy regression but was slower on CUDA: about 2.805 s per 5k all-force steps, so it was discarded.
  • The CUDA benchmark is short and intended for local directionality, not a publication snapshot.
  • Pairing still costs roughly 0.61 s per 5k steps on 1l2x; further work may need lower-level expression changes or OpenMM plugin work.

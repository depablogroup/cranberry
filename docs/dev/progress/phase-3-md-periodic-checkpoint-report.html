MD Periodic Checkpoint Review

Developer review for the Quan/EvgeniaWT restart-file investigation and tentative fix.

Reproduction

  • Unpacked /tmp/user_uploaded_attachments/slack/md-out-EvgeniaWT.zip and inspected home/quantang1903/cranberry/pdb/cg_6spn/md-out-EvgeniaWT.
  • The requested 200,000,000-step run has args.json, output.dcd, log, and detailed.log, but no checkpoint.chk or final.pdb.
  • The last standard log entry is step 19,700,000, so the run stopped at about 9.85% of the requested production length.

Root Cause

The MD runner previously wrote checkpoint.chk only after simulation.step(steps) returned. Long runs interrupted before completion could therefore contain trajectory and log reporter output but no checkpoint or final PDB.

Change

simulation.reporters.append(DetailedEnergyReporter(result.detailed_log_path, report_interval, append=detailed_append))
simulation.reporters.append(app.CheckpointReporter(str(result.checkpoint_path), report_interval))

_write_args(result.args_path, run_args)
simulation.step(steps)
simulation.saveCheckpoint(str(result.checkpoint_path))

The added OpenMM CheckpointReporter refreshes checkpoint.chk at the same interval as the trajectory and log reporters. The explicit final saveCheckpoint() remains, so completed runs still end with a latest checkpoint.

Docs

  • Updated quickstart restart guidance to note that checkpoints are refreshed during the run.
  • Updated output reference and MD tutorial wording to distinguish periodic checkpoint refresh from completed-run final PDB generation.

Verification

  • python -m pytest tests/test_md.py tests/test_cli.py -q: 20 passed.
  • python -m pytest -q: 38 passed.
  • Short EvgeniaWT CPU run with --steps 2 --report-interval 1 produced checkpoint.chk and final.pdb.

Risks

  • If a job is interrupted before the first report interval, there still will not be a checkpoint. Users should choose a report interval appropriate for the queue/runtime risk.
  • OpenMM checkpoint portability remains platform/system dependent.

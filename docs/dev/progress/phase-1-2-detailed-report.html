Executive Summary

What is now in place

  • A clean Python package project, independent from the legacy OpenMM-CGRNA repo.
  • Installable package metadata in pyproject.toml.
  • A working cranberry CLI with real inspect subcommands.
  • Packaged CRANBERRY alpha model assets and canonical example PDBs.
  • Canonical input validation based on OpenMM PDB parsing.
  • Local and GitHub CI checks for tests and documentation.

What is intentionally not in scope yet

  • No public 5SPN/RACER compatibility API.
  • No JAX/training/PySAGES functionality in the base package.
  • No public website build/deploy yet; docs currently build locally and in CI.

This section reviews the code that now defines the package boundary. These are the files to understand before porting force-field construction.

pyproject.toml: install contract

The package now declares the distribution name, import package discovery, CLI entry point, OpenMM dependency, optional extras, and explicit runtime data inclusion.

]

[project.scripts]

[tool.setuptools.package-data]
cranberry = [
  "data/README.md",
  "data/examples/*.pdb",
  "data/forcefields/*.h5",
  "data/xml/*.xml",

  • Why it matters: the wheel can be installed from scratch and still find cranberry.xml, the H5 parameter file, and fixtures.
  • Review note: package-data patterns are intentionally explicit so generated __pycache__ files do not enter wheels.
  • Open question for later: when conda packaging starts, mirror the same runtime data contract in the recipe.

cranberry/data/resources.py: resource lookup boundary

This module removes the old D_CGRNA assumption. Code asks the installed package for data paths instead of assuming a source checkout layout.

def data_path(relative_path: str) -> Path:
    resource = resources.files(_DATA_PACKAGE).joinpath(relative_path)
    if not resource.is_file():
        raise FileNotFoundError(f"Packaged data file not found: {relative_path}")
    return Path(_STACK.enter_context(resources.as_file(resource)))
  • Why it matters: this works in editable installs, wheels, and future zip-safe/resource-backed installs.
  • Design tradeoff: a process-lifetime ExitStack keeps extracted resources alive for libraries that require real filesystem paths.
  • Next usage: force-field construction should use this instead of string-building package-relative paths.

cranberry/forcefield.py: model registry and names

The registry is deliberately small. It maps a public model name to packaged assets and defines stable public force-group names.

FORCE_GROUP_NAMES = (

_MODEL_REGISTRY = {

  • Why it matters: callers can ask for default without knowing file names.
  • Compatibility contract: force-group names are public; integer force-group IDs are not.
  • Next usage: CranberryForceField should resolve model specs through this registry.

cranberry/validation.py: canonical input gate

The validator is intentionally strict about the CRANBERRY topology convention but allows a known terminal-phosphate edge case at chain starts.

REQUIRED_VIRTUAL_SITES = {"BC", "BN"}
EXPECTED_BEADS = {
    "A": {"P", "S3", "S2", "R1", "A1", "A2", "BC", "BN"},
    "G": {"P", "S3", "S2", "R1", "G1", "G2", "BC", "BN"},
    "C": {"P", "S3", "S2", "Y1", "C1", "Y2", "BC", "BN"},
    "U": {"P", "S3", "S2", "Y1", "U1", "Y2", "BC", "BN"},
}
if missing == ["P"] and residue in chain_start_residues:
    warnings.append(
        f"chain {residue.chain.index} first residue is missing terminal phosphate P"
    )
elif missing:
    errors.append(
        f"residue {residue.index} {residue.name} missing expected beads: {', '.join(missing)}"
    )
  • Why it matters: bad inputs fail before system construction, where errors would be harder to understand.
  • Current behavior: missing P at a chain start is a warning, not an error.
  • New v1 requirement: preparation should offer an option to add a 5'-terminal phosphate when sugar-pucker physics requires phosphate context.

cranberry/cli/main.py: first real command surface

The CLI remains mostly roadmap placeholders, but inspect is now implemented and acts as the first user-visible diagnostic surface.

inspect_parser = subparsers.add_parser(
    "inspect", help="inspect package data, models, or inputs"

  • Why it matters: users can verify installation, packaged assets, and input validity before MD code exists.
  • Exit-code contract: inspect input returns 0 for valid input and 1 for invalid input.
  • Next usage: prepare, cg, md, remd, and energy should follow the same thin-CLI-over-library-functions pattern.

Risk Review From Code Reading

Known risks

  • cranberry-v1-alpha.1.h5 is a copied alpha asset; final v1 parameter bundling is still pending.
  • Validation checks topology convention, not physical correctness.
  • OpenMM is now a base dependency because validation and future MD require it.
  • The public docs are skeletal; developer docs carry most design detail for now.

Mitigations already in place

  • CI installs from scratch and runs tests/docs.
  • Runtime assets are included in wheel builds.
  • Legacy executable output generation is documented separately via the GPU workshop path.
  • Developer docs and ADRs explain why the package/API/output choices were made.

Developer Workflow Update

This review also covers the new developer operating guide requested after comparing Karpathy-style lightweight program instructions and the third-party CLAUDE.md behavioral checklist against Cranberry's needs.

FileChangeReason
docs/dev/program.md New developer-only operating guide, including a Cranberry-specific Simplicity First section. Separates detailed agent workflow, scope rules, success criteria, simplicity rules, and experiment protocol from the short top-level instructions.
AGENTS.md Points non-trivial work to both docs/dev/program.md and docs/dev/cranberry-v1-plan.md. Keeps the auto-read entry point concise while preserving the design and workflow context needed for future sessions.
Important policy choice: the new guide borrows the useful parts of lightweight agent programs, such as explicit assumptions, surgical changes, and measurable success criteria, but does not copy an autonomous keep/discard loop for normal package work. Cranberry changes can affect scientific behavior, so the existing user-approved code-review workflow remains the default.
